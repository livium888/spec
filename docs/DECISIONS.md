# Decision records

## D1 — FSRS implementation: Dart `fsrs` port behind `Scheduler`, not fsrs-rs via FRB
- **Chosen:** `fsrs` 2.0.1 (MIT, open-spaced-repetition/dart-fsrs), 21 params (FSRS-6), wrapped by `DartFsrsScheduler`.
- **Rejected:** fsrs-rs + flutter_rust_bridge. Needs NDK cross-compile, Rust toolchain in CI, and cannot be verified without an Android device/emulator. Gains the optimizer, which v1 does not use.
- **Finding (verified against fsrs-rs `inference_v6.rs`):** the Dart package's default weights are py-fsrs defaults with decay `w[20]=0.2`, NOT the spec's 0.1542. We inject fsrs-rs `FSRS6_DEFAULT_PARAMETERS` (decay 0.1542) explicitly.
- **Known divergences from fsrs-rs** (verify against current docs): the Dart port floors elapsed time to whole days for retrievability and treats `<1 day` as same-day; fsrs-rs uses fractional days. Intervals can differ slightly from Anki's. fsrs-rs main now also ships a v7 model; v1 targets v6.
- **Measured divergence vs fsrs-rs 6.6.2** (12-review sequence incl. two lapses, same weights; reference vectors are in `test/fsrs_scheduler_test.dart`): max stability error 0.99%, max difficulty error 0.037. Cause: the Dart port clamps D0(4) inside the difficulty mean-reversion step; fsrs-rs uses it unclamped (about -4.79 with default weights). Effect on intervals is within ~3%. Accepted for v1; it matters if/when parameters are optimised with fsrs-rs, because they would be fitted to slightly different dynamics.
- **Revisit if:** the optimizer is needed (engine phase) -> add an `FsrsRsScheduler`, or replace the port with a ~100-line own implementation of the published FSRS-6 formulas validated against the same vectors; the interface already allows both.

## D2 — Deterministic fuzz
Library fuzz uses `Random()`, which breaks "replay == live". Library fuzz is disabled; the adapter applies fuzz seeded by `(cardId, reps_before)`.

## D3 — Replay inputs
Replay needs only `review_log` + `fsrs_params`. Learning steps, max interval and weights live in `fsrs_params.params_json`; changing any creates a new params row. `suspended`/`buried_until` are NOT scheduling fields (not derivable from log) and are left untouched by rebuild; leech suspension is applied live only.

## D4 — Schema additions beyond the spec
`card.step` (learning step index; required by FSRS), `setting(key,value)` (so settings travel in backups). Nothing removed.

## D5 — Undo
Undo sets `revoked_at` on the last log row, then rebuilds that one card by replaying its remaining non-revoked logs. One code path for undo and full rebuild.

## D6 — Backup format
Single SQLite file via `VACUUM INTO` (consistent snapshot, no WAL leftovers), named `learning-backup-YYYYMMDD.db`. Zipped DB+JSON rejected: the DB already contains everything; JSON adds a second source of truth.

## D7 — Threat model notes
- JSON import: untrusted text (LLM output). Strict schema validation, length caps, no HTML rendering (plain `Text`), no code execution. Clipboard read only on explicit tap.
- Restore: untrusted file. Open read-only, check `PRAGMA user_version`, `PRAGMA integrity_check`, required tables present, before replacing the live DB; keep the previous DB as `.pre-restore` until success.
- SAF: only the user-picked tree URI with persisted permission; no broad storage permissions.
- Backups are unencrypted (offline, user-owned folder). Revisit if the folder is cloud-synced.

## D8 — Where use cases live
Pure logic (scheduler interface, `applyRating`, queue ordering math, import validation, prompt rendering, engine contracts) is in `lib/domain` with no Flutter/Drift imports. Use cases that must run SQL (`ReviewService`, `QueueService`, `ImportService`, `BackupService`, `EngineFeaturesService`) live in `lib/data` rather than behind repository interfaces: a second abstraction layer over Drift would double the code for no swap-ability we need in v1. Revisit if a second storage backend appears.

## D9 — Spec ambiguities resolved (change if you meant otherwise)
- "Every session start: write an interest_log prompt": implemented as a one-tap, skippable dialog at the END of a session, per domain touched; a row is written only when you tap.
- `cards_surviving_30d`: cards first answered >30 days ago that are now in `review` and not suspended.
- `retention_30d`: share of review/relearning-state answers rated Hard/Good/Easy.
- Import rule "no card without a quote or URL" applies to `quote`/`url` source types; `model_memory` cards are allowed without one but are tagged `unverified`.
- Manual "Add card" reuses the import pipeline (source "manual entry").
- A new card's `due` equals its note's `created_at`; replay depends on this.
- Android Auto Backup is disabled (`allowBackup=false`) so no data leaves the phone except your SAF folder.

## D10 — Not verified in this environment (verify on device)
Android SDK downloads are blocked in the build container, so the APK build, SAF folder picker/writer, WorkManager weekly job and release signing are untested here. Host-side tests cover the logic: replay==live, undo, queue, import, backup/restore acceptance (export, wipe, restore, identical counts/dues/review count).

## D11 — "Learn something new": rule-based planner, not a learned model
- **Chosen:** `LearnPlanner` (pure, `lib/domain/learn_planner.dart`). Candidate actions per syllabus topic: *new topic*, *deepen*, *remediate*. Hand-set scores: new = 1.0 + 0.3·interest + up to 0.2·staleness; deepen = 0.2 + 0.8·(share of target still missing); remediate = 0.9 + severity (leeches/5 + lapse rate). Ties are broken by a hash of (day, topic), so equal options rotate from day to day but never change within a day.
- **Gates:** a topic opens only when every prerequisite is done or has >= 70% of its target cards; at most 2 topics in progress per domain (WIP limit); only the first eligible topic in outline order per domain is offered, so the curriculum order is respected.
- **Two options:** best candidate, plus the runner-up on a different topic. With probability 0.15 (seeded by day) the second slot is a random other candidate, flagged "A change of pace". This produces unbiased comparison data for a later learned policy and keeps the app from locking onto one domain.
- **Capacity:** `cardsRoom = floor((budget_minutes*60 - due_reviews*avg_sec) / (3*avg_sec))`; 3 = assumed reviews a new card costs in its first week (heuristic, not measured). `avg_sec` is the 30-day mean of logged review durations (12 s default until 20 reviews exist). If room < 3 the screen warns but still allows a small prompt.
- **Same day, same plan:** seed = logical day index. An issued-but-unimported prompt (< 24 h) is shown first with "Show it again / Discard".
- **Logging:** every choice writes `engine_decision` (`planner-1`, seed, capacity, all candidates with features, all scores, shown keys, explore flags and eps, whether the user chose manually, prompt id). Enough to fit weights or do off-policy evaluation later.
- **Rejected:** reinforcement learning / knowledge tracing now. Published methods rely on many learners or on simulated ones to get past the cold start (see the literature summary in the chat); with a single learner there is nothing to fit for months. Revisit once there are a few hundred logged decisions.
- **Revisit if:** the user keeps overriding the top option (the `manual` flag), or WIP limit / 70% gate feels too strict.

## D12 — Outline first
Topics come from an LLM-written outline (`outline-v1` prompt, imported as JSON `{domain, items[{title, level, description, target_cards, prerequisites[]}]}`). Costs one extra paste per subject; gives the app a definition of "covered / not covered". Validation: 1-60 topics, unique titles, levels 1-3, target 3-30, prerequisites must be titles, no self references and no cycles (also checked against existing topics before writing). Unknown prerequisite titles are dropped and reported. A wrong outline is the biggest risk, so the preview shows every topic and its prerequisites before anything is saved, and topics can be marked done/reopened later.

## D13 — Linking imported cards to topics
LLMs rephrase titles. Resolution order: normalised title match -> the topic of the latest unimported prompt in that domain -> a new topic (only if the JSON names one). This prevents phantom topics. Status is derived from card counts (`todo -> active` on first card, `-> done` at target); a manual "done" is never overridden.

## D14 — Restore accepts older backups
Restore refuses only backups from a NEWER schema; older files are migrated by Drift on reopen and then replay-checked. (The first version of restore rejected any version mismatch, which would have made every backup unusable after the first schema change.)

## Threat-model additions
- Outline JSON is untrusted: size caps (60 topics, 120-char titles, 300-char descriptions), strict types, no markup rendering, cycle detection before any write, all writes in one transaction.
- Prompts embed user-controlled text (source text, goal, existing titles, problem cards) into a template with single-pass substitution, so a value containing `{n}` or similar is never re-expanded. The LLM's answer is the real untrusted input and is validated on import.

## D15 — Topics are never "used up": rest, then return deeper
- **Lifecycle:** `todo -> active -> done -> (rest) -> active (round n+1) -> done ...`. A finished topic becomes eligible for a **revisit** after a rest of `base_months x 2^(round-1)` (default base 3 months: 3, 6, 12, 24 ... months), capped at **12 years**. The learner can force "Go deeper now" from the Topics screen at any time.
- **A revisit asks for NEW cards**, not repeats: the prompt says "round N, go deeper (mechanisms, applications, edge cases, misconceptions)", lists the topic's existing cards as do-not-repeat (up to 60), and import still dedupes by normalised front. Prompt version is logged as `v1+deeper`.
- **Mechanics:** choosing a revisit raises the topic's target by the round size (5-10 cards) and sets `rounds+1`, status `active`, so an unimported revisit shows as unfinished work ("deepen") instead of vanishing. The rest clock restarts when cards are imported (`MAX(note.created_at)` for the topic).
- **Scoring:** revisit = (0.5 + up to 0.4 for being overdue + up to 0.1 interest) x subject weight, so it competes below a brand-new topic (1.0) but wins when there is nothing new, or when a subject has been neglected.
- **Learner controls (Settings -> Subjects and topics):** per subject *Off / Low / Normal / High* (score x 0 / 0.6 / 1.0 / 1.4; Off pauses prompts, reviews of existing cards continue), a *Bring finished topics back later* switch, a per-topic *Skip* (never offered, does not block later topics), and a global first-rest length (1-24 months). Topics show "Comes back in about N months".
- **Schema v3:** `domain.learn_weight`, `domain.revisit`, `syllabus_item.rounds`; tested v1->v3 and v2->v3 migrations; restore of older backups still upgrades.
- **Rejected:** fixed "every N days" repetition of the same prompt (would produce duplicate cards); randomly resurfacing finished topics (unpredictable, ignores how long it has been). The doubling rest mirrors how spaced repetition itself treats cards.
- **Revisit if:** the rest feels too long or short (change the base months), or reviews pile up (lower retention or pause subjects; cards never disappear on their own).
- **Lifelong load, honestly:** the app has no card limit, but reviews do not shrink on their own. Mature cards have long intervals, so the daily load grows slowly with the collection; "Learn something new" already limits new cards to the study-time budget left after due reviews.

## D16 — Study advisor: when to add more, when to stop, and why
- **Verdicts:** *Good time* (go), *Go gently* (small batch, max 5), *Hold off* (wait), *Done for today* (stop). Each carries plain-language reasons, shown on Home (compact, "Why?" expands), on the prompt screen, after a review session, and as the gate when you press "Learn something new" while it advises against.
- **Inputs:** reviews due today and their time; minutes already studied today (logged durations) against the daily budget; new cards already added vs today's limit (which shrinks with backlog); reviews already scheduled for the next 7 days; retention over 30 days vs target (only with >= 50 answers); leech count; days since the last session.
- **Rules (hand-set heuristics, not fitted):**
  - stop: today's new-card limit is reached (or 0); or the budget is used up with nothing due; or too little time is left for even a few cards.
  - hold off: due reviews alone are > 90% of the budget; or retention is more than 7 points below target; or the next 7 days already hold >= 80% of the budget in reviews.
  - go gently: retention 3-7 points below target; >= 8 leeches; away more than 10 days.
  - otherwise go: up to `min(time left / (3 reviews x avg seconds), what next week can absorb / 3, new-card limit left, 10)` new cards, and the reason names the constraint that binds.
- **Why a 7-day look-ahead:** new cards cost most of their reviews in the first week, so judging only today's time says "yes" right up to the point where next week becomes impossible. 3 reviews per new card in week one is an assumption; the logged data can replace it.
- **Autonomy:** the app never refuses. When the advice is hold off or stop, pressing the button shows the reasons and offers "Add just 3 cards anyway". Fixing hard cards (remediation) is still offered when the advice is "hold off", because it reduces load; it is not offered when the advice is "stop".
- **Revisit if:** the thresholds feel wrong in daily use. They are constants in `StudyAdvisor`.

## D17 — One press, no choosing
"Learn something new" picks the top-ranked topic and shows its prompt immediately (count capped by the advisor), with the reasons. Choice stays optional: "Try something else" (runner-up), "See all options", and a manual topic picker. The first press on a fresh install adds all bundled subjects (15; the name-it-yourself language template is excluded) so there is always something to pick; each can be turned off in Settings -> Subjects and topics. An unimported prompt from the last 24 h is shown again instead of generating a new one. This replaces the earlier "show two options" screen, at the user's request.

## D18 — Release pipeline
New pushes cancel older builds (`concurrency`), and the rolling `latest-apk` release is updated in place (`gh release upload --clobber`) instead of deleted and recreated, so a cancelled run cannot leave the release empty.

## D19 — Card prompt v2: engaging cards, richer answer side, personal examples
- **Problem:** v1 produced bare Q&A pairs ("soulless"). Chosen: a teacher/storyteller prompt with 7 ranked principles, four dull-vs-great worked examples from different fields, a variety rule, a self-check, and an accuracy rule (vividness never outranks accuracy).
- **Answer side:** new optional fields `why_it_matters`, `example`, `memory_hook` (<= 600 chars each; stored in `fields_json`; shown after reveal under labelled headings). No DB migration: the importer ignores unknown keys, so older prompts and hand-written JSON keep working.
- **Personal relevance:** optional "About you" text (<= 300 chars, Settings) is added to card prompts so examples and analogies fit the learner. It is sent to whichever LLM the user pastes prompts into; the setting says so.
- **Guard rails:** a test extracts the JSON example embedded in the prompt and runs it through the real importer; it checks the example's `back` obeys the prompt's own length rule; the repair prompt (`remediate-v2`) follows the same principles.
- **Rejected:** forcing a "why" on every card (mixed evidence, slower reviews); long answers with the story inside `back` (hurts retrieval and grading); fixed per-subject tone presets (more settings, little evidence).
- **Risks:** longer prompts are followed less closely by some models; vivid stories raise hallucination risk (mitigated by the accuracy rule and the Unverified tag); examples can be copied (mitigated by "never reuse" and the variety rule).
- **Revisit if:** a model keeps ignoring the extras, cards feel formulaic after a few weeks (rotate examples), or `why_it_matters` becomes filler. Template versions are logged per prompt (`prompt_log.template_version`), so batches can be compared.

## D20 — Visual design and the "healthy habit" question
- **Reframing:** the goal is a daily habit people keep because it feels good and works, not compulsion. Engagement tricks (guilt streaks, variable rewards, leaderboards, spend-able currency) are rejected.
- **Evidence (retrieved):** gamification has small-to-moderate effects on learning (g about 0.25-0.5), the weakest on motivation and behaviour (Sailer & Homner 2019); one meta-analysis found better results with four or fewer game elements (Yu et al. 2023). Hence a deliberately small set: (1) a forgiving streak, (2) a daily progress ring, (3) a few real milestones, (4) a session summary. Nothing else.
- **Forgiving streak:** one missed day is bridged once the run before it is >= 3 days, at most once per 7 active days; the forgiven day is not counted. Copy never scolds. The advisor's "Done for today" is a feature: stopping is celebrated, not discouraged.
- **Visual identity:** warm paper neutrals + one vermilion accent (amber in dark mode); Fraunces (soft serif) for headlines and card text, Inter for controls; bundled fonts (SIL OFL), so still offline. Each subject has its own colour family and icon (colour by subject id so neighbours differ). Rating buttons are colour-coded AND labelled with the next interval.
- **Structure:** bottom navigation (Today / Progress / Library); Settings from the Today header. Today = one hero (ring, count, streak, one button), a Learn tile, the advice card, subject tiles. Progress = streak, 17-week activity heatmap, memory strength (long-term = stability >= 21 days), 7-day forecast, milestones. Review = large serif card, tap anywhere to reveal, haptics, session summary with a short confetti (skipped when the system asks for reduced motion).
- **Checks that run in CI:** every text/background colour pair and every subject colour family meets WCAG AA contrast (tests); tap-target size and labelled targets (Flutter guidelines) on Today and Review; no overflow at 160% system text size; reduced-motion behaviour.
- **I can see what I build:** `SCREENSHOT_DIR=... flutter test test/screenshots/screens_test.dart` renders the real screens with the real fonts to PNG (skipped in CI). Viewing them found real defects (identical rating buttons with unreadable labels, an invisible chart bar, a card that ignored taps on its own text). Whether it is *beautiful* still needs your eyes on a phone.
- **Rejected:** heavy animation libraries (Rive/Lottie: size, offline assets, little benefit), leaderboards (single user), points or currency, guilt notifications, per-subject mascot characters.
- **Not built yet:** a daily reminder notification at a chosen time (the single strongest habit cue; needs a notification plugin and an Android 13 permission prompt), sounds, widgets, custom app icon and splash.
- **Revisit if:** the streak or ring starts to feel like pressure (make them optional in Settings), or the user wants more variety (more subject colours/themes).

## D21 — Learn-view speed, and editing / deleting cards
- **Speed:** "Learn something new" ran four correlated subqueries per syllabus topic, each rescanning note / card / review_log (no index on note.syllabus_item_id). Measured 34 s at 25,000 cards, 200 topics, 800,000 log rows. Now one grouped pass per fact (cards and leeches per topic, last-covered per topic, 30-day reviews from review_log_time_idx): 1.0 s on the same data. Remaining cost is queue build plus stats (about 0.3 s each). Host numbers; a phone is slower.
- **Edit:** text only (question, answer or cloze text, and the three optional extras). Scheduling columns are never touched, so history and replay stay valid. Same length limits and the same cloze rule as import. A cloze edit may add a gap (a new card is created with `due` = note.created_at, which rebuild relies on) but may not remove one that already has a card.
- **Delete:** permanent, whole note (all cloze cards), with its review_log rows, in one transaction; review_log has a foreign key to card, so history cannot outlive its card. The dialog names what goes and points to Suspend for a temporary break. Older backups still hold the data.
- **Rejected:** soft delete with a `deleted_at` flag (every query in the app would need the filter, a schema migration, and the user asked for deletion); deleting a single cloze card out of a note (leaves a note whose text still hides a gap with no card).
- **Not built:** undo for delete (the confirm dialog is the guard), bulk delete, editing which topic a card belongs to.
- **Revisit if:** users delete by mistake (add an undo snackbar backed by a 10-second tombstone), or bulk clean-up is needed.

## D22 — Stats cache and streamed, compressed backups (scale work)
- **Stats cache:** Home and Progress scanned the whole review_log (distinct active days, total count, heatmap) on every refresh. Now `activity_bucket` (schema v4) holds answers per 15-minute bucket, caught up incrementally from `review_log` by a watermark (highest counted log id) stored in `setting`, updated in the same transaction. Undo uncounts the row; deleting cards invalidates and the next read rebuilds from the log. 15-minute buckets, not hourly: a day rollover at a :30 or :45 UTC offset would otherwise fall inside a bucket. Measured at 25,000 cards / 800,000 reviews: stats 1,041 ms -> 132 ms warm (the first call after upgrade builds the cache once, about 1.1 s here; seconds at tens of millions of rows). `review_log` stays the source of truth; the cache is disposable (`invalidate()`).
- **Still O(cards) per refresh:** the card-state counts, forecast and per-subject table scan the card table. Fine to roughly 100k cards; at 1M they would need their own incremental counters. Not done: no evidence yet that it matters.
- **Backups:** file-to-file through `saf_stream` `pasteLocalFile` / `copyToLocalFile`, so no backup is ever held whole in memory; the snapshot (`VACUUM INTO`) is gzip-compressed while streaming to a temp file that is deleted afterwards. 85 MB -> 12 MB on synthetic data (real cards compress less; expect 3-4x). New files are `learning-backup-YYYYMMDD.db.gz`; restore detects gzip by its magic bytes, so older plain `.db` backups still restore, and a corrupt archive is refused before the live database is touched. Retention (8) counts both kinds.
- **Verify against current docs / on a device:** `saf_stream` 4.0.2 `pasteLocalFile` and `copyToLocalFile` behaviour (overwrite semantics, very large files) is read from its source, not exercised. Tests use a plain directory storage; the SAF path has still never run on a phone.
- **Rejected:** SQL triggers to maintain counters (would also fire during restore/replay and hide bugs), a separate stats isolate (adds complexity before it is needed), zip with several files (no benefit over one gzip).
- **Revisit if:** the card table exceeds ~100k rows (add incremental card-state counters), or backups of a real multi-year database are still too large (move old review_log rows into yearly summaries).

## D23 — A library that never runs out (growth step)
- **Problem:** the starter outlines are finite (about 2,000 cards). When the learner had covered everything, the Learn screen asked them to browse the starter library or type a subject: a dead end, and a chooser they did not want. The starter library also advertised "about N cards", which read as a ceiling.
- **Decision:** when no card-level option exists (everything covered or resting), the one press produces an OUTLINE prompt automatically, chosen by `GrowthPlanner` (pure, seeded, logged to `engine_decisions` as `growth-v1`):
  1. `resume`: a subject that was started but never received its outline is asked for again (an abandoned prompt must not strand an empty subject).
  2. `expand`: more topics for a used-up subject, picked by weight + interest + staleness - size, with seeded jitter; the batch leans towards one of six rotating angles (advanced, applications, people and history, misconceptions, neighbouring areas, practice) so repeated batches differ.
  3. `discover`: every third growth step starts a brand-new subject from a built-in catalog of 197 subjects in 11 areas (not an LLM call), rotating through areas so none is neglected; never a subject that already exists.
  The learner sees why ("Why this one") and chooses nothing. "See all options" shows the growth step as one more card. Under "wait" / "stop" advice the advice is shown and the learner decides (an outline adds no cards but leads to more).
- **Prompt:** `outline-v2` lists at most the newest 100 existing titles (a lifelong subject can hold thousands) and says to cover different ground. Near-duplicates beyond the listed titles are possible; exact duplicates are dropped on import.
- **Copy:** the starter library says "Starts with N topics" and explains that the library keeps growing; the topics list says "N cards so far" instead of "N of target".
- **Honest limit:** this removes the dead end, not the work. At the 1M-in-40-years pace (68 new cards a day) that is roughly one outline round trip every 3-4 days (about 25 topics each) plus a daily card paste, and the review time is still the binding constraint (see the lifetime simulation).
- **Rejected:** asking the LLM to propose subjects (an extra round trip and an unpredictable list; the catalog is offline and testable); auto-importing without the learner pasting (offline-only app, no network calls); expanding while topics remain (adds clutter with no benefit).
- **Revisit if:** the catalog runs out (the planner then returns nothing and the screen says so), expansion batches feel repetitive (add angles or send more title context), or the every-third-step discover ratio feels wrong (it is one constant).

## D24 — The "map" prompt (new subjects chosen by the learner's LLM) and the in-app guide
- **Idea (from the user):** when the library needs breadth, give the LLM a summary of everything the learner has (subjects, topics; never cards) and have it propose what is missing. It replaces the fixed 197-subject catalog as the source of NEW subjects, removing that hidden ceiling. The catalog now only supplies "areas you have not touched" hints (one name per area) inside the prompt.
- **Bounded, not "everything":** the summary is capped (about 9,000 characters): the 12 most recently active subjects with their 10 newest topic titles, the rest with 3 titles or by name only, and a count of what was cut. Reasons: a 5-year library holds ~12,000 topics (~100,000 characters); long prompts make LLMs answer worse (Liu et al. 2023 TACL "Lost in the Middle"; Du et al. 2025, length alone degrades performance even with perfect retrieval); paste limits of chat apps are unknown; and the whole learning history would be sent to a third party each time. Paused subjects are marked "do not propose more of this".
- **Trigger:** every third growth step (not only "when everything runs out", which almost never happens now that used-up subjects are extended). Between, `expand` still asks for more topics for one subject. Nothing proposed if every subject is paused.
- **Answer format:** `{"subjects":[{"domain","why","items":[...]}]}`, up to 8 subjects, each validated by the same strict outline checks; preview with a tick-box per subject (new vs added to an existing one, "why", first topics); saved all-or-nothing in one transaction. The map prompt is closed on import. `prompt_log.domain_id` became nullable (schema v5, `alterTable`) because the prompt is about the whole library.
- **Guide:** "How it works" (Today header ?, Settings, prompt screen) plus a one-time "New here?" card on Today. It documents the daily loop, the three prompt kinds, how the library grows, editing, backups, pasting problems and privacy. It must be updated whenever a flow changes (it names buttons).
- **Weak points:** an LLM may propose generic subjects or near-duplicates of the learner's (rule 1 asks it not to; the learner can untick); a weak model may ignore the schema (the preview shows exactly what failed); the prompt discloses subject names and recent topic titles to whichever LLM the learner pastes it into (shown in full beforehand).
- **Rejected:** sending all titles (size, quality, privacy); sending cards (huge, pointless for choosing subjects); a fixed catalog only (a ceiling); LLM suggestions with no preview (untrusted input must be reviewed).
- **Revisit if:** proposals are often poor (add the learner's best-liked subjects as examples, or ask for fewer, better ones), or the every-third cadence feels wrong (`discoverEvery`).

## D25 — Fitting the memory model to the learner (like Anki's "Optimize")
- **What Anki does [Likely, from memory; verify against the current Anki manual]:** its FSRS "Optimize" button fits the algorithm's parameters to the user's own review history (fsrs-rs, by minimising prediction error), recommends having on the order of a thousand reviews first, and suggests re-running it every so often as the history grows. Parameters are per preset. The FSRS maths itself is documented by its authors; the Consensus search I ran surfaced related work from the same group (Ye et al. KDD 2022; Su et al. IEEE TKDE 2023: a memory model fitted to review logs) but not Anki's manual.
- **Decision:** the same capability, offline, in Settings > Memory model, plus a recommendation that always says WHEN and WHY, as days or as reviews, whichever is still missing (`OptimizerAdvisor`, pure, hand-set).
- **Forward model:** `fsrs_model.dart` re-implements the scheduler's update rules as lean arithmetic (the `fsrs` package is far too slow for thousands of passes). A test replays 40 random weight sets over random 30-answer histories through BOTH and requires stability and difficulty to agree to 1e-9 after every answer. It also asserts our weight bounds equal the library's.
- **Fit:** Adam on the 21 weights, with finite-difference gradients (22 passes per step; no autodiff library), seeded mini-batches of whole cards, a gentle pull towards the defaults that is stronger when there is little data, and clamping to the valid ranges. Loss = log-loss of the predicted recall (answers that came a day or more after the previous one; same-day repeats update the state but are not scored). Settings (500 steps, lr 0.025) were tuned on a simulated learner (81% of the gap to the true weights closed vs the defaults on unseen histories; lr 0.1 and above diverged).
- **Safety net:** 20% of cards are held back; new weights are only offered if they beat the current ones on those unseen cards by at least 1% relative log-loss (and at least 150 held-out predictions exist). Otherwise: "your current settings are already a good fit". The learner then chooses: Use / Keep. Applying inserts a NEW `fsrs_params` row (old rows are immutable) and repoints `active_params_id`; every old review keeps its `params_id`, so replay == live is unchanged (tested, including a review under the new weights). Cards are NOT re-derived under the new weights (Anki re-computes memory states; we do not, to keep the log replay exact): they adjust as they are reviewed. "Go back to the built-in settings" does the same in reverse.
- **When (advice rules):** first fit at 1,000 usable reviews (answers after a gap of at least a day; an estimate of 0.75 x answers on Today, exact on the Memory model screen). Later fits need >= 30 days and >= max(1,000, 30% of the history at the last fit) new usable reviews, but a prediction gap of >= 4 points (model expectation vs actual recall, >= 300 reviews, >= 14 days since the last fit) brings it forward. The numbers are this app's own conservative choices, not Anki's. Today shows a dismissible nudge (snooze 14 days) only when a fit is due.
- **Scale:** at most 150,000 reviews are read (whole cards sampled by id when there are more). Measured on this host with 800,000 reviews: status 1.3 s, fit 5.5 s in an isolate; a phone is slower (expect tens of seconds).
- **Limits (honest):** individual weights are not uniquely identifiable (decay trades off against stability), so the fit is judged by predictions, not by weights; a learner who always presses Good gives the fit little to learn from; a fit on little data can still overfit despite the pull towards the defaults; the on-device fit has not been run on a phone.
- **Rejected:** re-deriving every card under the new weights (breaks log replay and is slow); automatic silent re-fitting (the learner should see the check and decide); per-subject weights (too little data per subject); a native/Rust optimiser (build complexity for a one-off minute of compute).
- **Revisit if:** fits on real phones take too long (reduce steps or batch), the advice nags or stays silent too much (the constants are at the top of `optimizer_advice.dart`), or users want per-deck presets.

## D27 — "Stuck on one topic": the renamed-subject trap
- **Report:** every press of "Learn something new" seemed to offer the same topic.
- **Investigation (simulation with the real planner and 15 starter subjects):** (A) when every answer is imported, the presses rotate through all 15 subjects (staleness raises untouched subjects), so selection works; (B) when the prompt is copied but the answer is NOT imported, the same prompt is shown for 24 hours by design (the screen says so and offers "Discard and pick again"); (C) when the AI renames the subject in its answer, the cards were imported as a NEW subject, the requested topic stayed untouched, and the same topic came back every time. (C) was a trap in the import, not in the planner.
- **Fix:** if the answer's subject is unknown, it is matched to a recent unimported card prompt (24 h) when the topic title is the same or the subject names contain one another; the preview says so ("These go to X; the AI wrote Y"). A genuinely different subject is never forced into an old one, and nothing is remapped when no prompt is outstanding.
- **Honest note:** the one-press flow always takes the top-ranked option; the seeded "explore" pick only affects the second option shown under "See all options". Variety comes from the staleness bonus, which only works once answers are actually imported. A recency penalty or weighted-random pick could be added if the rotation ever feels too predictable.

## D28 — Phase 2: keeping review time sustainable (forecast, retire, per-subject target recall)
- **Why:** the lifetime simulation showed review time, not storage, is the limit of a lifelong library. The app now says so in numbers and gives three levers. (Defaults I chose where the learner did not answer: the app SUGGESTS cards to retire and asks, never retires on its own; target recall is per subject only, not per topic.)
- **Looking ahead (Library or Progress):** a seeded Monte Carlo over the same FSRS-6 arithmetic as the scheduler (`nextState`, `retrievability`, `intervalDays` in `fsrs_model.dart`; the single-step helpers are tested against the verified forward model). Inputs: a sample (up to 3,000) of existing review-state cards with their stability, difficulty, due day, last review and subject target recall (each stands for several real cards); new cards a day (the learner's actual pace over 28 days, else the daily setting); the active weights; seconds per review from the learner's own answers (12 s until 20 exist); the daily-minutes budget. Output: reviews and minutes a day at 6 months, 1, 2, 5, 10 years; the first moment the smoothed daily time passes the budget ("in about 14 months"); and the new-cards-a-day that keeps the 5-year load inside the budget (binary search over simulations). Headline numbers average 3 seeds because a single small-library run has about +-10% noise. A what-if slider re-runs with 1 seed (about 40 ms).
- **Validated against ground truth:** the same learner is run through the REAL scheduler (learning steps, interval rounding, `applyRating`): the forecast is within 12% of it at 90% and 80% target recall (10 new cards a day, long run). Fixing the learning-step model (one same-day step lifts stability; 2 reviews for a new card) is what closed the gap at 80%.
- **Simplifications (honest):** recalled answers are 6% Hard / 84% Good / 10% Easy; extra "Again" presses while learning and lapse relearning beyond one same-day step are not modelled; all reviews happen on their due day (no lateness, no vacations); fuzz is ignored; cards you will add are assumed to behave like average new cards of the learner's subjects. Treat the numbers as estimates (rounded in the UI).
- **Retire:** a card is "mastered" when its stability is >= 1, 2 (default) or 3 years, it has >= 6 reviews and <= 1 lapse. Retiring sets `suspended = 1` and `retired_at` (schema v6): the card leaves reviews, nothing is deleted, scheduling fields and history are untouched (tested: replay == live and exact restore, including that a card the learner suspended or a leech is never touched by retire or restore). The screen states the honest saving (365 / stability reviews a year per card; mature cards are cheap, so it is modest but grows with the library) and asks for confirmation. Restored cards keep their due date and are simply due if it has passed.
- **Per-subject target recall:** `domain.retention` (schema v6, null = app-wide). The subject's reviews use a params row with the SAME weights and steps but that retention (created once, reused, looked up by weights + retention within 1e-6, retention stored to 3 decimals and limited to 0.70-0.97); each review logs the row it used, so replay is exact (tested with two subjects and real reviews: the lower target gives longer gaps and `rebuildAll` finds nothing wrong). After a memory-model fit the subject variants are created again from the new weights on first use. Applies to reviews from now on; cards already scheduled keep their due date. The forecast uses each card's own target.
- **Rejected:** retiring automatically; an analytic closed-form forecast (cannot capture interval growth and lapses together); per-topic retention (too fine for the data); deleting mastered cards (irreversible); a forecast run on every Today refresh (kept to the Looking ahead screen).
- **Revisit if:** forecasts disagree with real life (compare a year of actual reviews to what it predicted; the rating mix and lateness are the first things to fit), the retire thresholds feel wrong, or learners want a suggested subject for lowering recall.

## D30 — Phase 3: pictures on cards and reading aloud (arts, crafts, languages)
- **Scope (decided with the learner's earlier request for arts, music, languages, crafts):** pictures and speech. NOT in this phase: audio clips for music (needs a playback plugin and file picking; revisit after this is proven on the phone) and pictures that arrive inside an AI's JSON (the app is offline, so an AI cannot supply real images).
- **Pictures:** `media` table (schema v7) holds the bytes (SHA-256 unique, mime, created); a note refers to one by hash in `fields_json` (`image`, `image_side` front or back, `image_alt` up to 300 characters). Why a table and not files: every backup and restore, and the streamed gzip, carries pictures with no change to the backup format; replay and scheduling are untouched. The picker (`image_picker`, system photo picker, so no storage permission) shrinks to at most 1,280 px at JPEG 80 while picking, typically 100-300 KB; a 1.5 MB hard limit and a magic-bytes check (PNG, JPEG, WebP, GIF) guard the rest. Pictures are removed when nothing refers to them (edit, replace, delete card), checked by scanning notes for the hash. Cost to know: JPEGs do not compress in the backup, so 1,000 pictures add roughly 150-300 MB; Diagnostics shows the count and size. Card text is still plain `Text`; a picture is an `Image.memory` of bytes the learner chose, decoded at most 1,080 px wide; tap for full screen with pinch zoom; screen readers announce the description.
- **Reading aloud:** `flutter_tts` uses the phone's own text-to-speech engine (offline once a voice is installed; the app has no network code). Per subject: language (19 offered, BCP-47) and which side is written in it (the question or the answer); a speaker button on the card, and an optional global "Read aloud automatically". Rules: a cloze is read as the whole sentence; when the language side is the ANSWER, the speaker is disabled until the answer is shown and a tap on it never falls through to reveal the card, so sound can never give the answer away. If the phone has no voice for the language, the message says where to install one.
- **Threat model:** pictures come from the learner's own gallery; bytes are never executed, only decoded by Flutter's image codecs after a signature check; text read aloud is card text the learner already sees.
- **Not verified on a phone:** both plugins compile only in CI; how natural the voices sound and whether each language's voice is installed depends on the phone; the system photo picker's behaviour across makers.
- **Rejected:** pictures as loose files (backup format change, orphan handling, restore verification), downloading pictures (offline rule), a speech service with its own engine (size, licences), choosing the speech language per card (too fiddly; per subject is how learners study).
- **Revisit if:** backups get too large with pictures (then a size warning or a lower picture quality setting), or learners want audio clips (add playback and a file picker on the same `media` table: mime already stored).

## D32 — "Find a picture online": the first and only network use (exception to "offline only")
- **Request:** the learner asked for cards to be able to load pictures from the web. I advised against raw AI-written image URLs and they chose option A: a lookup the learner drives.
- **Why not URLs from the AI:** measured fabrication rates for AI-written URLs and references are 3-13% fabricated URLs with search tools attached and 28-55% fabricated or wrong references from memory alone (Rao et al. 2026 arXiv, Seifi et al. 2026, Chelli et al. 2024; not measured for image URLs specifically, which are probably worse). A live URL that shows the WRONG picture is worse than a dead link and nothing in the app can detect it. And there is no "signal" when a web file changes: the only real signal is the learner editing the card.
- **Decision:** the AI may add `image_query` to a card (2-6 plain words for a Commons search; never a URL; prompt v3). On the Edit card screen, "Find a picture online" searches Wikimedia Commons, shows thumbnails, then a preview with credit and licence, and ONLY on "Use this picture" downloads one (about 960 px wide) into the existing `media` table. Everything after that is offline: reviews, backups and restores never touch the network, and the picture is kept even if the web page changes or disappears. Re-checking = running Find again on edit (no automatic re-checks, no background traffic).
- **Safeguards (the threat model):** (1) the learner must agree once (a dialog says what leaves the phone: the search words and, as with any web visit, the phone's internet address) and can switch it off in Settings; (2) all traffic goes through `SafeFetcher`: https only, hosts limited to `commons.wikimedia.org` and `upload.wikimedia.org`, no redirects (so a redirect cannot leave those hosts), no credentials in addresses, 20 s timeout, size ceiling enforced while streaming (400 KB previews, 1.5 MB kept), a descriptive User-Agent (Wikimedia policy); (3) the answer is untrusted JSON: parsed defensively, markup stripped from names and credits, only jpeg/png/webp wider than 400 px, never executed or opened as a link; (4) the downloaded bytes pass the same magic-byte and size checks as a gallery photo; (5) a web address in `image_query` or typed as a search is refused; an odd `image_query` is dropped quietly and never rejects a card; (6) nothing is stored until the learner confirms a preview.
- **Licence and answer-leak rules:** Commons files carry free licences, but CC BY and CC BY-SA require credit, so a credit line ("Author · Licence · Wikimedia Commons", plain text, 300 characters) is stored with the picture and shown under it. Found while rendering screenshots: the credit names the artist, which answers "who painted this?", so it is shown only after the answer is revealed (also in full screen). For the same reason the picture description is NOT prefilled from the file name (a screen reader would read out the answer); the learner writes it.
- **New permission:** `INTERNET` (release manifest). Nothing else changed in the manifest.
- **Version-sensitive (verify against current docs):** the MediaWiki Action API parameters and response shape (`generator=search`, `gsrnamespace=6`, `prop=imageinfo`, `iiprop=url|mime|size|extmetadata`, `iiurlwidth`, `formatversion=2`) and Wikimedia's thumbnail-size and User-Agent policies. I could not reach Wikimedia from the build sandbox, so the code is tested against fixtures and a local server only. First real use on the phone is the real test; the Phone check has an item for it.
- **Rejected:** (a) the app fetching raw AI-written URLs (wrong-picture risk, arbitrary hosts, SSRF-style input); (b) any host beyond Wikimedia (a long tail of licences and hot-link blocks; revisit with more allowed hosts one at a time); (c) automatic lookup for every imported card (surprise network traffic and a wrong picture nobody looked at); (d) re-fetching on a timer; (e) Flutter's `Image.network` (no host limits, no size cap, no User-Agent).
- **Not built (named, not silently skipped):** a batch "find pictures for all cards that have a hint" flow (each card is a manual step today); other sources (Europeana, museum APIs); showing a card's credit on the Browse list.
- **Revisit if:** Wikimedia changes or blocks the API or thumbnail sizes (then the error message shows and the manual gallery picker still works), learners want many pictures at once (add the batch flow), or one Commons hit rate is too low for niche topics (add a second source).

The answer comes back by share-in (the keywords preview opens by itself; share-in recognises the new `image_keywords` shape) or by "Paste the answer" (clipboard read only on that tap). A preview lists each card's question with its keywords, with every usable row ticked; unusable rows say why; the button says "Add keywords to N cards". Nothing is saved before that tap.
- **Rules that protect the learner's data:** only `fields_json` of a note changes (scheduling, review history and replay are untouched); existing keywords are never overwritten and a card that already has a picture is skipped, re-checked at the moment of saving (so a card edited since the preview is safe); the side hint is stored only if the card has no side yet; the whole commit is one transaction; entries are matched by the card's note number, which must exist, and an answer over 200 entries, a repeated number, a non-integer number or a keyword that looks like a web address is refused or skipped with the reason shown.
- **Threat model:** the answer is untrusted text (same strict, typed checks as other imports; keywords go through `cleanImageQuery`; nothing is executed or opened as a link). The prompt sends card text to whichever AI the learner chooses, exactly like the existing card prompts and the "About you" field; the screen says nothing is sent automatically.
- **Not built:** automatic keyword guessing on the phone (tried a guess from the question text in D32's first build and it gave nonsense); a per-card "suggest again".
- **Revisit if:** batches of 80 are too long for a chat window (lower the cap), or learners want the keywords for cards that already have a picture (they do not need them).

## D37 — "Go deeper": AI-suggested reading, checked against library catalogues (second network exception)
- **Request (answers to my questions):** per TOPIC (not per card); books AND articles; yes to extra network hosts for a catalogue check; the learner should not have to leave the app to read.
- **Evidence that shaped it:** AI-written references are often wrong (28% fully fabricated and 55% with some error from memory alone, hallucination up to 91% in older chatbots, worse on less visible topics; 3-13% of AI-written URLs invented even with search tools; see the Consensus results cited in the conversation). So every suggestion is labelled an AI suggestion, the prompt tells the AI to leave the list empty unless certain, and the app checks existence itself. Quality ("trusted authors, no marketing") cannot be verified by a catalogue; it is only requested in the prompt and the screen says so plainly.
- **Prompt v5:** one optional `further_reading` list per answer (so once per topic): 2-3 items, each `kind` (book, textbook, article, review, course), author, exact title, one-sentence why. Prefer standard textbooks, academic presses, peer-reviewed reviews, university lectures; never blogs, listicles or marketing; never a web address, DOI, ISBN, edition or year; empty if not certain. It is optional and can never make a card import fail: a wrong shape gives an empty list, odd entries are skipped, at most 4 are kept, the same work twice is kept once.
- **Storage (schema v8):** table `reading_item` (subject, optional topic, kind, title, author, why, normalised key unique per subject, check status and result, read flag). It touches no cards, notes or scheduling; backups carry it with everything else. A work suggested again is not duplicated.
- **Check:** "Check it exists" (one entry) or "Check all" asks Open Library (books and textbooks; `search.json` by title and author) then Crossref (articles and reviews, and books it did not find; `works` by bibliographic query). A hit needs the TITLE to match (subtitles and small words ignored; equal or 80% overlapping word sets) AND the first author's SURNAME to appear in the catalogue's authors; otherwise "not found: the title or author may be wrong". Courses and other kinds say they cannot be checked automatically. The screen says what "found" means and does not mean (listed, not good).
- **Network (second exception to "offline only"):** only when the learner taps a check, only after a consent dialog naming both sites and what is sent (title, author, and the phone's internet address), switchable in Settings ("Check reading suggestions online"). Allowed hosts, in their own constant `kReadingHosts`, separate from the picture hosts: `openlibrary.org`, `api.crossref.org`. Same `SafeFetcher` limits (https only, no hosts but those, redirects re-checked, size cap, timeouts). Answers are untrusted JSON, parsed defensively (work ids and DOIs matched against strict patterns). Crossref's polite pool asks for a contact address; none is sent (only the app's user-agent); verify against current docs.
- **Reading without leaving the app:** "Look it up" opens the catalogue page (Open Library, where books can often be borrowed) or the DOI link in an Android in-app browser tab (Chrome Custom Tab, `url_launcher` `inAppBrowserView`): it slides over the app and Back returns to the list. The app fetches nothing from those pages, so no extra hosts are needed. Only https pages are opened. Verify against current docs: Custom Tabs need a Chromium browser on the phone; otherwise the phone's browser opens.
- **Not built:** an offline reader that saves open-licence article text into the app (copyright and extraction work; revisit if learners want to read on the train); a reading timer ("5 minutes then back to your cards"); per-card suggestions; reading suggestions on the review screen (never in the middle of a review).
- **Threat model:** AI text and catalogue answers are untrusted (type-checked, length-capped, addresses rejected, never rendered as markup); the only addresses opened are catalogue/DOI https links built by the app from validated ids, never an address the AI wrote.
- **Revisit if:** catalogue matching rejects real works (loosen the title rule) or accepts wrong ones (tighten), the Open Library or Crossref API changes, or learners want to read inside the app without Chrome.

## D38 — Simplify pass: fewer things at the first level, plain words
- **Request:** "Do the simplify pass first" (after the design-critique answer: too many equal-weight entries, jargon, a warning tag on every card).
- **Chosen:** (1) Library in three groups: Add to your library / Manage (Browse, Reading list, Image keywords, Subjects and topics) / **Advanced** (collapsed: Looking ahead, Retire mastered cards). (2) Settings: **Advanced** (collapsed, at the bottom) holds Memory model and Diagnostics and phone check; the top keeps only "How the app works". (3) Plain wording: "Desired retention" -> "How much to remember (target recall)"; "Learning steps" -> "Steps for new cards"; "Relearning steps" -> "Steps after forgetting"; per-subject "Target recall" -> "How much to remember"; card state "Relearning" -> "Forgotten". (4) The "Unverified" tag is gone from the review screen.
- **Rejected:** hiding the memory-model and scheduling fields entirely (some learners tune them; collapsing keeps them one tap away); deleting Looking ahead/Retire (they are the answer to a growing review load, only rarely needed); a "pro mode" switch (a second code path to test for no gain).
- **Cost, stated plainly:** "Unverified" marked cards the AI was unsure about. It is still stored and shown in Browse/Import preview, but a learner now studies such a card without a warning on its face. If wrong facts reach reviews, bring back a quiet icon after the reveal.

## D39 — Prompt v6: written for the model, with "search if you can"
- **Request:** tell the AI to search the web when it can; and write the prompts to be efficient for the LLM that reads them, not for a human, to get the best cards back.
- **Evidence (Consensus, verify against current docs):** search removes most fabricated references (grounded systems score near 100% on "the source exists"), but it does not make claims correct: with web search about 30% of individual statements were still unsupported and 30.6% of citations distorted their source; provider explained 88-96% of citation-quality variance. So the search line is conditional and never raises trust: without a check, time-sensitive claims cannot be "high" confidence, and reading suggestions are still checked against a catalogue by the app. Prompt format matters, but there is no universally best format: results vary by model, and the effects are real (format sensitivity up to tens of accuracy points in some models); zero-shot can match few-shot while examples help output-format reliability.
- **Chosen (v6):** instructions first, in priority order; the task's own inputs (existing cards, source text) last, fenced in tags and declared to be data, not instructions (also limits prompt injection through pasted source text); ONE fixed output contract with a basic and a cloze example, kept because worked format examples make structured output reliable; the four weak/strong pairs cut to two (the JSON examples already carry the other two); persona and flourish removed; a final one-line instruction after the data. About 18% fewer characters (10.3k -> 8.4k). Outline `outline-v3` and repair `remediate-v4` get the same search line, plain-text rule and data-not-instructions line.
- **Citation markers:** chat apps that search can leave reference tokens inside strings, which would break or pollute the import. The prompt forbids them and every importer (cards, outline, plan, keywords) removes the unambiguous ones (private-use cite tokens, 【…】) before parsing. Plain "[1]" is kept because it can be real card text.
- **Not measured:** I cannot call an LLM from here, so whether v6 returns better cards than v5 is untested. The restructure follows published guidance and the studies above, not an A/B result. Test: run v5-style and v6 for the same topic on your LLM and compare.
- **Revisit if:** v6 cards are blander or fewer than v5's (restore the persona line and the two removed example pairs first), or your LLM leaves markers the stripper does not know.

## D40 — Review screen: learn-ahead, inline undo, "about this card" (Phase A items 1, 2, 6)
- **Request:** learn-ahead for cards waiting on a learning step, an undo on the review screen itself, an explanation of the Learning state with SuperMemo-style statistics.
- **Learn-ahead:** when nothing else is due (no learning, no review, no new card in today's allowance), learning/relearning cards due within N minutes (Settings, "Show waiting cards early", default 20, 0 = off, max 60) are offered now, soonest first. A card answered less than a minute ago is not offered again at once (that is repetition, not spacing). Cards offered early are not counted as "come back later". Scheduling is unchanged: the answer is replayed from the log like any other, and a test checks replay == live for an early answer. Cost: an early review of a short step is slightly less spaced than the step intended; that is the same trade Anki's learn-ahead makes. **Rejected:** always showing waiting cards (breaks the step spacing and bypasses the new-card limit); a longer default (a 30-min wait is no longer "this session").
- **Inline undo:** after each answer a bar "Rated Good · Undo" shows for 6 s above the answer buttons (not over them, so no button moves under the thumb). It calls the existing undo, which revokes the last log row and rebuilds the card from the log. The top-bar undo icon stays for anyone who needs longer (WCAG 2.2.1 timing: the timed bar is a convenience, not the only way). It is a polite live region. **Rejected:** a snackbar (it covers the buttons).
- **About this card (tap the state tag):** the state in plain words (using the learner's own step lengths), then FSRS numbers for that card: chance of recall now (retrievability), memory strength (stability: days until recall falls to 90%), difficulty (1-10 with a word), next review, times answered and forgotten, pass rate and average time from the log, a forgetting curve with the learner's target and today's position, and the last 8 answers. The vertical axis starts below the lowest value shown (labelled) so a slow fade is visible. The sheet says the numbers are model estimates, not measurements.
- **SuperMemo:** the three quantities (stability, retrievability, difficulty) are the "three component model of memory" of Wozniak's SuperMemo; FSRS uses the same three, so these are real model values, not an imitation of SuperMemo's own screens. SuperMemo's item and global statistics (e.g. A-Factor, retention graphs, workload) are NOT copied. Verify against current docs. Library-wide counterparts already exist in Progress and Looking ahead.
- **Threat model:** no new external input; everything shown is derived from the learner's own review log and card.
- **Not built (needs your call):** library-wide SuperMemo-style statistics (retention by interval, a forgetting-index trend); a two-button rating mode; session size; keyboard shortcuts (Phase A items 3-5).
- **Revisit if:** learn-ahead makes sessions feel repetitive (lower the default), or the curve confuses (replace it with two sentences).
